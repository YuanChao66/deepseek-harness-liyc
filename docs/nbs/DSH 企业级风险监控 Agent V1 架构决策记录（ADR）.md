## ADR-001　DSH Runtime 与单插件架构

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：项目定位为"基于 DeepSeek Harness 构建企业级风险监控 Agent"。DSH 是底层 Agent Runtime，插件是能力承载单位；需确定工程到底以什么形态交付、绑定到 DSH 的哪一层。
- **决策**：以 DSH 为唯一 Agent Runtime；交付物为单个 TypeScript 插件包（`src/index.ts` + `package.json`），不另建运行时，不引入独立 Java 工程。技术基线为 DSH 工作树 live 源码（核验快照 fcc0ad46，后续源码更新不视为自动变更基线）。
- **后果**：
  - 正面：复用 DSH 的 Tool Registry、生命周期、配置与注入机制，避免重复造运行时。
  - 负面：插件行为受 DSH 模型语义约束；DSH 升级与插件升级的兼容边界需在 DOC-16/DOC-17 单独跟踪。
- **备选方案**：建设独立 Java 风险平台 + DSH 只做模型侧（被否决，成本与范围超出 V1）。
- **关联**：DOC-02 §7；DOC-01 §2、§21。

## ADR-002　四层架构和依赖规则

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：需把业务逻辑与 DSH Runtime、外部系统解耦，保证领域规则可独立测试、外部依赖可替换、故障可隔离。
- **决策**：采用四层架构 **Plugin/Tools → Application → Domain**，Infrastructure 实现 Application 定义的 Port。Domain 不依赖 Infrastructure/DSH；Application 不依赖具体 Adapter；Composition Root 是唯一装配点。
- **后果**：
  - 正面：清晰分层、可测试、可替换外部依赖。
  - 负面：引入 Port/Adapter 间接层，短期成本上升；需用架构测试固守模块边界（禁止反向依赖）。
- **备选方案**：领域层直接调用 Infrastructure（被否决，破坏可测试性与可替换性）。
- **关联**：DOC-02 §3、§5、§6；DOC-01 §3。

## ADR-003　单 Agent、单插件、模块化

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：V1 范围明确不建设多 Agent 协同、多实例分布式、独立 Web UI。需确定内部组织方式。
- **决策**：运行时为单进程、单实例、单 Agent、单插件；内部采用模块化设计，模块间通过公开 `index.ts` API 通信。
- **后果**：
  - 正面：简化并发、一致性与部署复杂度。
  - 负面：单实例是并发与容量的硬上限；未来扩展多 Agent/多实例需另立 ADR 并重新评估一致性与恢复语义。
- **备选方案**：V1 即引入 Kafka/多实例（被否决，违反 V1 范围边界）。
- **关联**：DOC-02 §8；DOC-01 §2.2、§14.1。

## ADR-004　DSH 原生 Tool Registry

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：九个模型工具需对 Agent 暴露，需确定工具注册与发现的技术路径。
- **决策**：使用 DSH 原生 Tool Registry（`ctx.tools.register(defineTool(...))`，`inject=['tools']`，返回注销函数）；不另建 MCP Tool Server，不自行实现 Tool Registry。
- **后果**：
  - 正面：复用 DSH 工具发现、调用、Schema 校验、渲染与注销机制。
  - 负面：工具契约受 DSH Tool Schema/渲染模型约束；错误映射与取消/超时行为受 DSH 能力边界限制（见 ADR-007、DOC-16）。
- **备选方案**：自建 Tool Registry 或独立 MCP Tool Server（被否决，违反 DOC-01 §3.3 与附录 A 核心原则）。
- **关联**：DOC-02 §7.2；DOC-01 §3.3、§6。

## ADR-005　Task / Workflow / Scheduler 分离

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：编排域存在三个易耦合的关注点：何时触发、执行哪些 Stage、单个 Task 生命周期与执行策略。混用会导致调度策略、流程拓扑、任务状态机互相纠缠。
- **决策**：三模块严格分离——Scheduler 决定何时触发；Workflow Engine 决定执行哪些 Stage、顺序和依赖；Task Engine 管理单个 Task 的生命周期、并发/优先级、超时/取消、重试退避、Checkpoint、幂等与崩溃恢复。Collector Runner 负责实际 Collector 执行，Collector 本身不管理任务生命周期。
- **后果**：
  - 正面：三模块可独立测试与替换；触发决策与执行策略解耦。
  - 负面：编排层抽象增加，需明确三者协作契约（由 DOC-04 细化）。
- **备选方案**：单一 Job 引擎统一管理（被否决，职责交叉，难以演进）。
- **关联**：DOC-02 §4.2（MOD-APP-002/003/004）；DOC-01 §14。

## ADR-006　JSON 持久化与 Storage Engine

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：V1 存储介质选择。需在简单可审计与 ACID 能力之间取舍。
- **决策**：采用 JSON/JSONL 文件持久化，单写者模型、临时文件 + Flush/Sync、原子替换、完整性校验、必要的文件锁、Append-only History。SQLite 仅作为未来扩展方向，不属 V1 必须依赖。文件持久化不冒充 ACID 数据库。
- **后果**：
  - 正面：零外部依赖、可审计、可备份；契合单实例运行。
  - 负面：不承诺跨文件 ACID、跨外部系统 ACID；崩溃恢复、原子替换语义需在目标 OS/文件系统上验证（DOC-11）。
- **备选方案**：直接采用 SQLite 作为主存储（被否决，超出 V1 依赖边界，但保留为未来扩展）。
- **关联**：DOC-02 §10；DOC-01 §13。

## ADR-007　YAML 配置和热更新

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：配置需支持安全热更新，且不得破坏已运行任务的稳定性。
- **决策**：YAML 为唯一主要配置格式；配置变更流程为"读取 → Schema 校验 → 业务校验 → 生成不可变配置快照 → 原子切换 → 记录审计"；失败回退 Last Known Good；已启动 Task/Workflow 继续使用启动时固定的配置快照。历史事实（RiskEvent、Proposal History）不因热更新被覆盖。
- **后果**：
  - 正面：运行中可安全迭代配置；审计可追溯。
  - 负面：快照机制增加内存与版本管理成本；Schema 演进需版本化（DOC-14）。
- **备选方案**：重启生效（被否决，运维时效不足）。
- **关联**：DOC-02 §7.5、§10；DOC-01 §14.4、§16。

## ADR-008　多租户和安全边界

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：租户是业务数据与风险数据的隔离基本边界；必须内建，而非运行时追加。
- **决策**：租户为隔离基本边界；Repository 不提供无租户约束的通用入口（如无条件 findById/findAll）；TenantContext 仅由可信 Application/Security 边界建立，Tool 参数中的 tenantId 不得作为授权依据；跨租户访问显式授权并留审计；认证与授权分离；Secret Provider 与 Data Masking Service 独立；关键操作审计 fail-closed。
- **后果**：
  - 正面：默认安全、隔离可靠、审计完整。
  - 负面：每个 Repostory 操作需显式租户范围，接口一致性压力增大（由 DOC-07 固化）。
- **备选方案**：仅靠工具入参过滤租户（被否决，可被伪造，违反 DOC-01 §12.2）。
- **关联**：DOC-02 §7.3、§10；DOC-01 §12。

## ADR-009　Risk 与 Action Proposal 分离

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：风险事实、发生周期、攻击活动、处置建议需要可独立追溯，且风险判定必须确定化、可审计。
- **决策**：RiskEvent（风险事实）、RiskCycle（风险发生周期）、AttackEvent（攻击活动）三者分离，不合并为单一状态实体；Action Proposal 与风险事实分离管理；Risk Score（确定性评分）与 Severity（等级）分离，转换由明确规则定义；状态机推断由状态机引擎执行，LLM 不得直接决定最终分数/等级/执行动作。
- **后果**：
  - 正面：追溯清晰、举证完整、恢复与再触发可隔离管理。
  - 负面：实体增多，关联与存储复杂度上升（由 DOC-03/DOC-06 承接）。
- **备选方案**：风险与处置合并为单一事件（被否决，无法表达恢复后再次发生与多主体攻击）。
- **关联**：DOC-02 §4.2/§4.3；DOC-01 §9、§10。

## ADR-010　V1 不执行真实风险动作

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：风险处置动作（锁号、封禁、限流、拦截）一旦误执行会造成业务损害，需明确 V1 的执行边界。
- **决策**：V1 只生成 Action Proposal（七态状态机），不执行锁号、封禁、限流、拦截等真实动作；Proposal 的 APPROVED 仅代表审批通过，不代表动作执行成功；V1 不得通过 Proposal 工具隐式执行真实业务动作；禁止将 SQL/Shell/Java 或任意可执行表达式作为 Proposal 内容直接执行。
- **后果**：
  - 正面：消除自动误伤风险；人工审批闭环清晰。
  - 负面：需明确 Proposal 到真实动作的人工/下游执行闭环（通知人工处理闭环见 DOC-01 §11.1）。
- **备选方案**：V1 即执行自动处置（被否决，风险不可控，超出范围）。
- **关联**：DOC-02 §2.2、§4.2；DOC-01 §10.3、附录 A 原则 13。

## ADR-011　九类结构化错误与分层错误处理

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：错误处理若不统一分类与分层，各模块会各自抛原始异常，导致错误不可定位、不可判定重试、无法稳定映射到 DSH Tool Response，也无法满足「业务结果 / 数据质量 / 错误分离」。
- **决策**：采用九类错误分类（`Validation` / `Authorization` / `NotFound` / `Conflict` / `Timeout` / `Cancellation` / `Persistence` / `ExternalDependency` / `Internal`），统一 `StructuredError` 结构化类型（`category` / `code` / `message` / `tenantId`（脱敏）/ `retryable` / `cause`），五段分层（Infrastructure 原始异常 → Application Error → Use Case 遏制 → Plugin Adapter → DSH Response）。Domain 不依赖 DSH 错误类型；`cause` 链仅进日志，不进模型可见输出。
- **后果**：
  - 正面：错误可分类定位、可判定重试（Task Engine 只重试瞬时 `ExternalDependencyError` 等）、可稳定映射到 DSH Response。
  - 负面：新增结构化错误类型与逐层转换成本；需在 Adapter 边界统一兜底转换，避免遗漏。
- **备选方案**：直接透传 DSH 错误类型（被否决，破坏 Domain 与 DSH 解耦，违反 DOC-02 §3.3）。
- **关联**：DOC-11 §3；DOC-07 §2.7；DOC-01 §15；DOC-16（Response 映射）。

## ADR-012　Journal / Outbox / Inbox 局部事务协调

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：文件持久化非 ACID（ADR-006），但采集、风险、Proposal、通知等操作需要「崩溃后不丢已提交、不重复执行、外部通知至少一次投递」。需定义写前意图日志、待投递队列与去重守卫的记录格式、提交顺序与恢复语义。
- **决策**：由 `PersistenceTransactionCoordinator` 统一协调；引入三类追加式记录——`Journal`（写前意图日志，`INTENDED/PERSISTED/APPLIED/ABORTED`）、`Outbox`（待投递通知，至少一次投递）、`Inbox`（已消费去重守卫）。固定提交顺序 `intent → prepare → persist → checkpoint → commit`；单文件原子替换 + 有序 `fsync` 保证局部一致；不承诺跨文件/跨外部系统 ACID。
- **后果**：
  - 正面：崩溃可恢复到底一致点、不重复、不丢失；外部通知至少一次投递可得。
  - 负面：写入放大（Journal/Outbox/Inbox 额外落盘）、恢复与对账复杂度上升。
- **备选方案**：直接采用 SQLite/WAL 作主存储（被否决，超出 V1 依赖边界，保留为未来扩展，见 ADR-006）。
- **关联**：DOC-11 §4、§6；DOC-07 §5；DOC-01 §13.6/§13.7；ADR-006。

## ADR-013　双 Hash 幂等语义

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：DOC-01 §13.4 要求「同 Hash 返回原结果、不同 Hash 拒绝冲突、处理中返回引用、UNKNOWN 先协调」。幂等键由五元组（租户+数据源+表+主键+源版本）确定性 Hash 得到；若仅有键 Hash，同一五元组必然算出同一 Hash，「不同 Hash → 拒绝冲突」从无触发场景。需补充内容指纹才能完整落地冲突语义。
- **决策**：采用双 Hash——`identityHash`（五元组 SHA-256，即 DOC-06 的 `IdempotencyKey`）+ `contentHash`（规范化幂等相关载荷 SHA-256，仅存于幂等记录）；幂等判定输出五态 `IdempotencyOutcome`（`NEW / DUPLICATE / CONFLICT / IN_PROGRESS / UNKNOWN`）。
- **后果**：
  - 正面：完整落地 DOC-01 §13.4，可检测「同键不同内容」的源侧完整性冲突（源内容变而未提升 sourceVersion）。
  - 负面：幂等记录多存一份内容指纹；需明确 contentHash 的规范化字段投影。
- **备选方案**：仅用五元组 Hash，冲突场景退回人工判断（被否决，无法满足「不同 Hash 拒绝冲突」）。
- **关联**：DOC-11 §5；DOC-07 §2.6/§3.2；DOC-06 §2.2.5；DOC-01 §13.4/§4.1.7。

## ADR-014　确定性崩溃恢复与故障注入验收

- **状态**：Accepted（草案）
- **日期**：2026-11-10
- **背景**：恢复机制的正确性必须可复现、可门禁；仅靠单元测试难以覆盖各崩溃时点的一致性。需定义确定性恢复算法，并以关键注入点固化验收断言（满足 DOC-01 §13.7 对故障注入要求的委托）。
- **决策**：启动按固定顺序恢复（加载 Last Known Good 配置 → Journal 重放 + 数据/Checkpoint 对账 → Inbox 恢复 → Outbox 恢复 → 重建游标续跑 → 开放业务 Tool）；恢复完成前不开放依赖持久化的业务 Tool；以 `FI-001～FI-011` 故障注入矩阵作为恢复验收断言（数据不丢、不重复、Checkpoint 不越界）。
- **后果**：
  - 正面：恢复行为确定性、可复现、可作为 CI/验收门禁。
  - 负面：需故障注入测试基建（TestClock/Fixture/故障注入已在 DOC-01 §18.2 预留）。
- **备选方案**：依赖人工验证恢复（被否决，不可复现、不可自动化门禁）。
- **关联**：DOC-11 §6、§7；DOC-04 §8.2；DOC-01 §13.7/§18.2；DOC-15。

## ADR-015　分层可观测与 Trace / Correlation 归因

- **状态**：Accepted（草案）
- **日期**：2026-11-11
- **背景**：DOC-01 §15.4 要求结构化日志、Trace ID、Correlation ID、Task/Workflow ID、Tenant ID（脱敏）、关键业务操作记录、采集与计算耗时、错误分类、恢复日志、配置变更记录，且不得输出敏感凭证。需决定 Agent 自身可观测如何结构化，并与被监控对象（SYS-MON）的领域指标区分。
- **决策**：自观测（结构化日志 + Trace/Span + Correlation + 归因 + 采样 + 自观测指标 + 覆盖率）与被监控对象观测（领域 `MetricResult`/`Event`）分离；采用双关联标识（`TraceId`=一次端到端流转、`CorrelationId`=跨链路因果链），并在日志中归因耗时（`durationMs`）与错误（DOC-11 九分类 + 稳定错误码）；采样按 `Config` 驱动，关键事件（错误/告警/恢复/配置变更/跨租户授权/人工干预）强制采样不丢弃。
- **后果**：
  - 正面：端到端可串联定位、错误与耗时可分类归因、自观测与领域指标不互相污染。
  - 负面：引入采样与额外指标/日志基础设施，归因字段增加了日志结构成本。
- **备选方案**：仅依赖 DSH 自身可观测（被否决，缺少领域级 Correlation 与错误分类归因）；全量 Span 记录不采样（被否决，高频采集成本过高）。
- **关联**：DOC-13；DOC-01 §15.4/§5.6；DOC-11 §3；DOC-12 §5/§9；MOD-APP-017/018、MOD-INF-009。
