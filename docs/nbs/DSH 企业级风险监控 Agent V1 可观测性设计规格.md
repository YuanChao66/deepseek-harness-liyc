## 1. 文档概述

### 1.1 编写目的

本文档定义 V1 风险监控 Agent 的横向可观测性规格：结构化日志的分级与记录结构、链路追踪与关联标识（Trace/Correlation/Task/Workflow/Tenant）、错误分类与耗时归因、采样策略、自观测指标与告警、监控覆盖率、持久化恢复日志与配置变更记录，以及主动诊断。

本文档落实 DOC-01 §15.4（可观测性）与 §5.6（监控覆盖率），并将 DOC-02 MOD-APP-018、MOD-APP-017、MOD-INF-009 展开为可执行的观测契约。

### 1.2 边界声明

| 主题 | 归属 |
| ---- | ---- |
| 结构化日志分级与记录结构、链路追踪、关联标识、采样、耗时/错误归因 | 本文档 |
| 自观测指标目录、监控覆盖率、告警 | 本文档 |

| 采样率、告警阈值、日志保留周期等取值配置 | DOC-14 |

本文档定义「Agent 自身可观测性」；被监控目标（SYS-MON-001～008）的指标结构与采集属领域逻辑（DOC-04/DOC-05），不在本文档范围，仅在 §3 区分。

DOC-01 §15.4、§5.6；DOC-02 §4.2/§4.4/§10（MOD-APP-016 Health、MOD-APP-017 Diagnostics、MOD-APP-018 Observability、MOD-INF-009 Observability）；DOC-11 §3（错误分类）；DOC-12 §5/§9（脱敏、审计与业务日志分离）。

### 1.4 术语

复用 DOC-01 §1.3、DOC-11 §1.4、DOC-12 §1.4 术语，新增：

| 术语 | 定义 |
| ---- | ---- |
| Trace | 一次端到端业务流转（采集→标准化→指标→规则→风险→报告/通知）的调用链 |
| Span | Trace 内的一个逻辑片段（一次采集、一次规则评估、一次投递等） |
| Correlation ID | 跨链路关联因果关系的标识（如风险事件→派生 Proposal→通知→报告） |
| 归因（Attribution） | 将耗时、错误、失败归到具体模块/分类/Task 的过程 |
| 自观测 | 对 Agent 自身健康与运行状态的观测（区别于被监控对象的观测） |
| 采样（Sampling） | 对 Trace/日志按策略决定是否完整记录的机制 |

## 2. 可观测性设计目标与原则

1. **结构化优先**：日志与指标均结构化、可机器解析，不靠自然语言检索。
2. **全链路可关联**：一次业务流转可经 Trace/Correlation/Task/Workflow/Tenant 唯一定位。
3. **错误可分类归因**：每次失败携带错误分类与稳定错误码，可聚合成错误分类统计（DOC-11 §3）。
4. **脱敏内建**：日志不输出敏感凭证，PII 脱敏，与审计分离（DOC-12 §5/§9）。
5. **确定性**：关联标识与归因由确定逻辑生成，不依赖 LLM。
6. **采样可配置**：采样率、告警阈值、保留周期均为 `Config` 字段（DOC-14），本文档不硬编码数值。
7. **自观测与业务解耦**：观测本身不改变业务结果，观测采集失败不阻断业务。

## 3. 可观测性范围与对象

### 3.1 自观测对象（本文档范围）

观测对象是 Agent 自身的运行状态，覆盖三类：

| 类别 | 内容 |
| ---- | ---- |
| 日志 | 结构化操作日志、错误、恢复与配置变更（§4、§8） |
| 链路 | Trace/Span、关联标识与归因（§5） |
| 指标 | 采集/计算/规则/通知/报告等健康与吞吐指标、监控覆盖率（§6） |

### 3.2 与被监控对象（SYS-MON）的区分

| 维度 | 自观测（本文档） | 被监控对象（DOC-04/05/06） |
| ---- | ---- | ---- |
| 观测对象 | Agent 自身进程与逻辑 | Java/Tomcat/Redis/MySQL/Nginx/Docker/ZooKeeper/Apache（SYS-MON-001～008） |
| 数据去向 | 结构化日志 + Trace + 自观测指标 | 领域 `MetricResult`/`Event` 持久化 |
| 标识 | Trace/Correlation/Logger | `MetricDefinition`/`DataSource` |

二者职责分离：Agent 采集被监控对象的指标走领域链路（DOC-05），Agent 观测自己走本文档链路。

## 4. 结构化日志

### 4.1 日志分级

| Level | 用途 | 示例 |
| ----- | ---- | ---- |
| TRACE | 细粒度调试（默认关闭/按 config 开启） | 单条记录标准化细节 |
| DEBUG | 运行调试 | 游标推进、幂等判定 |
| INFO | 关键业务操作记录 | 采集开始/完成、规则命中、通知投递、恢复完成 |
| WARN | 可恢复异常/退化 | 采集 PARTIAL、重试退避、监控目标失联 |
| ERROR | 操作失败 | 采集失败、投递失败、持久化失败 |
| FATAL | 不可恢复故障 | 进程级崩溃、恢复失败 |

约束：

1. 关键业务操作记录走 INFO（DOC-01 §15.4「关键业务操作记录」）。
2. 错误/失败日志携带错误分类与稳定错误码（§5.4）。
3. 分级对照 DOC-11 §3 错误分类：`WARN/ERROR/FATAL` 才与 `StructuredError` 关联；`INFO` 下的「规则未命中」等正常业务结果不记 ERROR。

### 4.2 日志记录结构

统一结构化日志记录（MOD-INF-009 实现）：

```ts
type LogLevel = 'TRACE' | 'DEBUG' | 'INFO' | 'WARN' | 'ERROR' | 'FATAL';

interface LogRecord {
  ts: Instant;                        // 事件时间
  level: LogLevel;
  logger: string;                     // 来源模块（如 'MOD-APP-006'）
  event: string;                      // 事件名（稳定）
  message: string;                    // 描述（脱敏后）
  tenantId?: TenantId;                // 脱敏策略下
  traceId?: TraceId;
  correlationId?: CorrelationId;
  taskId?: TaskId;
  workflowId?: WorkflowId;
  errorCategory?: ErrorCategory;      // DOC-11 §3，仅失败
  errorCode?: string;                 // 稳定错误码
  durationMs?: number;                // 耗时归因
  extra?: LogExtra;                   // 结构化上下文字段（脱敏后，见下）
}

interface LogExtra {
  [key: string]: string | number | boolean | null;   // 无嵌套，保证可解析
}
```

约束：

1. `extra` 只允许平铺标量，避免不可解析的嵌套与对象序列化噪声。
2. 所有字段经 DOC-12 §5 脱敏后输出；`tenantId` 遵循脱敏策略（DOC-01 §15.4）。
3. 严禁 `message`/`extra` 携带敏感凭证（DOC-01 §15.4「不得在日志中输出敏感凭证」）。

### 4.3 脱敏与审计分离

日志输出与审计分离（DOC-12 §9.3）：

- 业务应用日志携带脱敏后的运行信息（本文档 §4.2）。
- 审计记录走 `AuditRepository`（DOC-07 §3.10），append-only、fail-closed，独立于业务日志。
- 日志配置/权限/采集要求由 DOC-17（部署）接线，本文档只定结构与格式。

## 5. 链路追踪与关联

### 5.1 关联标识

```ts
type TraceId = Branded<string, 'TraceId'>;        // 一次端到端流转
type CorrelationId = Branded<string, 'CorrelationId'>;  // 因果链关联
```

| 标识 | 语义 | 载体 |
| ---- | ---- | ---- |
| TraceId | 一次完整业务流转（采集→标准化→指标→规则→风险→报告/通知） | 全链路 Span 共享 |
| SpanId | Trace 内一个逻辑片段 | 单段采集/评估/投递 |
| CorrelationId | 跨链路因果链（风险事件→Proposal→通知→报告） | 派生对象间共享 |
| TaskId / WorkflowId | 执行与调度归属（DOC-06 §3） | 触发器/任务/流程 |
| TenantId | 租户（脱敏） | 全链路 |

关系（示意）：

```
Trace ──(包含)──▶ Span（采集 Span / 规则 Span / 通知 Span）
Correlation ──▶ 关联同一风险事件的派生 RiskCycle / Proposal / Notification / Report
Workflow ──▶ Task ──▶ Span
```

约束：

1. 一次端到端流转必分配唯一 `TraceId`；每个逻辑片段分配 `SpanId` 并挂 `TraceId`。
2. 派生对象的因果链共享 `CorrelationId`（如规则命中产生 RiskEvent → 后续 Proposal/Notification/Report 使用同一 CorrelationId）。
3. 标识在流转边界生成/透传，日志、错误、恢复、配置变更四条线均携带，保证可串联（DOC-01 §15.4）。

### 5.2 耗时归因

关键耗时按 Span 归因，覆盖（DOC-01 §15.4「采集和计算耗时」）：

| Span | 记录耗时 |
| ---- | ---- |
| 采集 | 全部时长 + 游标推进前段（对齐 DATA_PERSISTED，DOC-04） |
| 标准化 | 事件标准化耗时 |
| 指标计算 | 单指标/单窗口计算耗时 |
| 规则评估 | 单规则评估耗时 |
| 通知投递 | 投递与重试耗时 |
| 报告生成 | 组装与渲染耗时 |
| 恢复 | 启动重放/对账耗时 |

每段在对应日志记录 `durationMs` 并写入 Span；耗时与业务结果解耦，观测采集不阻塞业务。

### 5.3 错误分类归因

1. 失败日志统一在 `errorCategory`/`errorCode` 归因（DOC-11 §3 九分类）。
2. 归因维度：模块（logger）、分类、租户、Trace/Correlation、Task。
3. 可据此聚合出「错误分类分布」「失败模块」「重试成功率」等自观测指标（§6）。

### 5.4 采样策略

1. Trace/日志按策略采样（高频采集 Trace 全量成本高）。
2. **强制采样**：错误、告警、恢复、配置变更、跨租户授权、人工干预等关键事件一律完整记录，不采样丢弃。
3. 采样率、强制采样清单均为 `Config` 字段（DOC-14），非硬编码（遵守 AGENTS.md「No hardcoded tunables」）。
4. 采样只影响 Trace 完整度，不变更已产生的错误分类与关键事件日志。

## 6. 指标与监控（自观测 Metric）

### 6.1 自观测指标目录

抽象维度沿用分层并发预算（DOC-02 §8.3、DOC-04 §7.1；默认值见 DOC-14 §4.12）：采集/指标/规则/通知/报告。

| 分层 | 指标示例 |
| ---- | ---- |
| 全局 | 进程心跳、启动/恢复耗时、恢复结果、租户公平性、并发预算占用 |
| 采集 | 采集成功率、PARTIAL/ERROR 比例、游标推进延迟、单源吞吐 |
| 指标 | 计算耗时、数据质量分布（NORMAL/STALE/PARTIAL/ERROR/INVALID）、派生指标 DAG 深度 |
| 规则 | 评估数、命中率、规则失败率、评估耗时 |
| 通知 | 投递成功率、重试次数分布、UNKNOWN 比例、渠道延迟 |
| 报告 | 报告生成耗时、成功率 |
| 覆盖 | 监控覆盖率（§6.2） |

约束：

1. 自观测指标与领域 `MetricResult` 分离：自观测指标不入领域指标链，领域指标也不冒充自观测指标。
2. 指标按租户、模块、Tag 维度汇总；敏感字段不入指标维度或经脱敏。

### 6.2 监控覆盖率

按 Target、组件、Metric、Rule 和 Collection Task 统计预期与实际覆盖（DOC-01 §5.6）；覆盖率聚合由 MOD-APP-016 Health 承担。覆盖率状态值域唯一权威为 DOC-03 §6 `MonitoringCoverage`（=DOC-01 §5.6）：

| 状态 | 说明 |
| ---- | ---- |
| 未配置 | 预期监控但未配置 |
| 未启用 | 已配置但未启用 |
| 采集失败 | 采集/评估失败 |
| 数据过期 | 已采集数据超出新鲜度阈值 |
| 规则缺失 | 应有规则未定义/缺失 |
| 正常 | 覆盖正常 |

未配置监控不得视为健康；覆盖率下降产生运行告警（DOC-01 §5.6）。覆盖率指标 = 实际覆盖 / 预期覆盖（按 Target/组件/Metric/Rule/Collection Task 逐维统计），用于暴露「应监控而未监控」的缺口。

### 6.3 指标上报

1. 自观测指标经 MOD-INF-009 结构化采集/上报，与领域指标链路物理分离。
2. 上报失败不阻断业务、不影响领域采集（观测与业务解耦）。
3. 指标保留周期、上报目标均入 DOC-14 配置。

## 7. 告警

1. 告警分级：按严重度（信息/警告/严重/致命）对应健康影响。
2. 告警触发源自自观测指标阈值或关键事件（恢复失败、投递 UNKNOWN 超限、监控覆盖率缺口、租户公平性劣化）。
3. 告警阈值、去重窗口、通知渠道引用由 DOC-14（配置）定义；告警本身的投递走通知链路并复用 DOC-12 §6 Secret。
4. 告警不改变业务状态，仅报告。

## 8. 持久化恢复日志与配置变更记录

### 8.1 持久化恢复日志

系统恢复过程记录（DOC-01 §15.4「持久化恢复日志」、DOC-11 §6）：

| 事件 | 记录内容 |
| ---- | ---- |
| 恢复开始/结束 | 触发原因、起始态、结束态、耗时、结果 |
| Journal 重放 | 各记录状态分布、payloadHash 对账结果、协调异常 |
| Inbox/Outbox 恢复 | PENDING/SENDING/PROCESSING→UNKNOWN 数量、重投结果 |
| Checkpoint 续跑 | 续跑位置、跳过的 CollectionCommit 状态 |
| 恢复失败 | 失败模块、错误分类、影响范围 |

恢复日志复用 §4.2 结构，`event` 前缀 `recovery.*`。

### 8.2 配置变更记录

配置变更记录（DOC-01 §15.4「配置变更记录」、DOC-12 §8）：

1. 配置热更新/变更在业务日志记 `config.changed` 事件（变更项、来源、版本、结果），供可观测串联。
2. 越权修改的拒绝与审计记录另行进入审计链路（DOC-12 §8/§9），不依赖业务日志。
3. 变更记录与审计分离，前者属可观测，后者属合规审计。

## 9. 健康与主动诊断

运行健康与主动诊断分属两个模块：

- 健康（MOD-APP-016 Health）：健康检查（TOOL-009），汇总进程心跳、恢复状态、各模块健康与监控覆盖率。
- 主动诊断（MOD-APP-017 Diagnostics）：按 Trace/Correlation/Task 聚合一次流转的耗时/错误/样本，输出诊断报告。

约束：

1. 健康与诊断均只读，不修改业务状态。
2. 诊断接口遵循 DOC-08（Tool 接口契约规格）/DOC-16（DSH 适配）的授权与脱敏要求。
