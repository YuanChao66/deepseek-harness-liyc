## 1. 评审结论（总体）

文档在**架构原则、依赖方向、安全与多租户边界、DSH 集成约束**上表述完整且质量较高，四层架构、事件不可变、风险事实/周期/攻击分离、V1 只生成 Proposal 不执行动作、LLM 不做最终判定等核心约束清晰，具备作为架构设计输入的条件。

但作为一份应"直接作为研发、测试工作依据"的 SRS，目前**尚不满足 §22 基线冻结条件**，主要原因是存在 **5 个阻塞级缺口（Critical）**：对外 9 个模型工具需求整体缺失、技术基线自相矛盾、风险状态机缺失、验收标准不可量化（AT/TBD 空壳）、文档版本状态不一致。此外还有 9 个重要问题（Major）与 6 个建议优化（Minor）。

**本次共识别问题 20 项**：Critical 5、Major 9、Minor 6。建议先修复 5 个 Critical，再推进基线冻结。

## 2. 阻塞级问题（Critical）—— 必须修订才能满足冻结条件

### C-1　9 个模型工具需求整体缺失（需求缺失）

- **位置**：全文（工具清单仅存在于《工程设计基线》§4，SRS 无对应章节）
- **类型**：需求缺失 / 边界缺口
- **现状**：`collect_business_data`、`collect_system_metrics`、`collect_application_logs`、`calculate_metrics`、`evaluate_risk_rules`、`query_risks`、`manage_action_proposals`、`generate_risk_reports`、`get_monitor_health` 这 9 个对模型暴露的工具，在本文档中**一次也未出现**。§17.4 仅引用 `AT-001～AT-076` 编号，但未说明这些验收用例对应哪个工具。
- **问题**：9 个工具是插件对外（Agent 侧）的核心契约，SRS 缺失其职责、入参、出参、幂等与错误语义，研发无法据以开工，测试无依据。这是 SRS 最严重的功能缺口。
- **建议**：新增"模型工具需求"章节（建议插入 §5 与 §6 之间），按工具逐一给出：
  1. 工具名与用途；
  2. 输入参数表（字段、类型、必填、校验约束）；
  3. 输出 canonical 结构（对齐 `defineTool` 的 `output.schema`）；
  4. 幂等/错误语义（成功、部分成功、失败、取消如何表达）；
  5. 关联 Application 用例（Use Case）与验收编号映射。
  并以 `get_monitor_health` 作为首个完整示例，其余 8 个至少给"用途 + 关键入参 + 关键出参"的骨架，明细可指向 DOC-04/DOC-05。

### C-2　技术基线自相矛盾，且与当前开发决策冲突（逻辑冲突 / 技术实现矛盾）

- **位置**：文档属性表（L11）、§2.3（L97）、§20.1（L1607-1613）、§20.2（L1633）
- **类型**：逻辑冲突 / 前后不一致
- **现状**：
  - §20.1 钉死 `v0.2.1-rc.5 + b830ec9`，并声明"不得使用 master 或其他版本的接口作为 RC.5 已验证依据"；
  - 但 §20.2 的核验结论引用 `packages/core/tools/src/index.ts` 等 **src 源码路径**（这来自工作树，而非 rc.5 发布 tag）；
  - §20.2 又写 Node 约束 `^22.19.0 || >=24.0.0`；
  - 与项目实际（`AGENTS.md` 要求 `node >=24.9`、基于 live 工作树源码开发）不一致。
- **问题**：核验对象究竟是 rc.5 tag 还是 live 源码，前后打架；Node 版本区间与项目约束不符；"不用 master"与"基于 live 工作树"互相矛盾。
- **建议**：统一为"**以当前仓库工作树 live 源码为技术基线**"，在 §20.1 记录当前 commit hash（替代 rc.5 表述，或把 rc.5 降级为历史记录）；Node 版本约束改为与 `AGENTS.md` 一致的 `>=24.9`；§20.2 每条结论标注其依据的源码路径与 commit；同步更新文档属性表"技术基线"栏。

### C-3　风险领域状态机缺失（需求缺失 / 数据定义不明确）

- **位置**：§8.2（L818-821）、§8.3（L822-832）
- **类型**：需求缺失
- **现状**：§8.2/8.3 仅说明 RiskEvent"表示风险事实及整体生命周期"、RiskCycle"表示一次具体风险发生周期"，但**全文未定义风险的状态枚举与状态转换规则**（`Pending/Normal/Triggered/Ongoing/Recovered/Unknown` 仅出现在《工程设计基线》§7.3）。
- **问题**：风险生命周期是核心领域模型，无状态定义导致 DTO、Repository、TestClock 测试、恢复判定均无法落地，直接违反 §17.6"关键状态机 90% 覆盖"的前提。
- **建议**：在 §8 新增"风险状态机"小节，明确：
  1. RiskCycle 状态枚举（与设计基线 §7.3 对齐：Pending/Normal/Triggered/Ongoing/Recovered + 独立 Unknown）；
  2. 状态转换规则表——哪些事件/评估结果触发转换、`Unknown` 的进入与退出条件、非法转换的处理（报错/拒绝）；
  3. "恢复"的判定输入（连续评估次数、无异常时长阈值、数据质量门槛、人工确认），把这些从 §4.2.10 的散点收口成统一契约。

### C-4　验收标准不可量化：AT 空壳 + TBD 未汇总（验收不可量化 / 前后不一致）

- **位置**：§4.1.8（L242-246）、§4.2.12（L378-380）、§4.3.10（L498-500）、§17.4（L1417-1425）、§19.4（L1546-1582）
- **类型**：验收标准不可量化
- **现状**：`AT-001～AT-076` 仅以编号区间出现，无任何具体用例内容；§22 基线冻结条件第 5、6 条依赖 AT 与 TBD，但全文大量 `TBD`（§4.1.8、§5.5、§16.5、§18.4 等）散落各处，§19.4 只定义了 TBD 登记表的**字段结构**，文档自身没有填出一张"当前 TBD 汇总表"。
- **问题**：无法验证、无法判断冻结条件是否满足；"验收覆盖"名存实亡。
- **建议**：
  1. §17.4 明确"AT 用例明细由 DOC-08 定义，本文档仅登记编号与 BR 的映射关系"，并给出 **2 个可量化验收示例**（含：前置条件、操作输入、预期输出、通过判据），示范验收粒度；
  2. 在文末新增"当前 TBD 汇总表"，将所有 TBD 编号化（`TBD-00x`）并标注类别、影响模块、优先级（P0/P1/P2）、是否阻塞冻结；正文 TBD 处改用 `TBD-00x` 引用回填。

### C-5　文档版本状态前后不一致（前后表述不一致）

- **位置**：文档属性表（L7-9）vs 附录 B（L1731-1741）
- **类型**：前后不一致
- **现状**：属性表为 `V1.2-Review`，但附录 B 版本表仅列出 `V1.0-Review / V1.1-Review / V1.1-Baseline`，缺失 `V1.2-Review`，也未给出下一基线版本规划。
- **问题**：同一文档两处版本状态不一致，破坏可追溯性。
- **建议**：附录 B 补 `V1.2-Review`（说明：并入《Java 企业级风险监控 Agent》独有内容，原稿归档），并补充计划中的 `V1.2-Baseline` 行。

## 3. 重要问题（Major）

### M-1　Proposal 7 态只有枚举、无状态转换规则（边界条件缺失）

- **位置**：§9.3（L969-981）
- **问题**：给了 `GENERATED/PENDING_REVIEW/APPROVED/REJECTED/WITHDRAWN/EXPIRED/SUPERSEDED` 枚举，但无合法转换路径、触发条件（如 EXPIRED 由什么触发、APPROVED 后能否 WITHDRAWN、谁可发起 SUPERSEDED）。§9.3 中"相同意图追加版本"与"已审批 Proposal 不得静默覆盖"二者的边界也未定义。
- **建议**：补一张状态转换规则表（当前态 × 触发事件 → 目标态，标注非法转换），并规定 EXPIRED 的超时阈值、SUPERSEDED 与"追加版本"的判定规则（同一 RiskEvent+Proposal 类型+适用对象 ⇒ 同意图）。

### M-2　金额精确十进制与 Metric 值类型未闭环（数据定义不明确）

- **位置**：§4.1.3（L199）vs §7.1 MetricResult（L744-756）
- **问题**：L199 要求"金额使用精确十进制语义，不使用浮点数"，但 §7.1 的 `MetricResult.value` 未定义类型；JSON 原生无 decimal，如何表示精确金额（string？`{value, scale}`？）未规定，导致金额派生指标无法无损落盘与比较。
- **建议**：统一规定精确小数的 JSON 表示（建议 string/定点 + 显式 scale，或明确采用库的序列化约定），并在 §7.1 增加 `value` 的类型与精度说明。

### M-3　时间与时区规范散落、未统一（数据定义不明确）

- **位置**：§7.1（L727-728）、§4.1.4（L207）、§12.2（L1100-1101）
- **问题**：UTC 存储、左闭右开、租户时区业务日分散在三处，但未定义时区标识标准（IANA tz？）、DST 处理、业务日切点、`eventTime/collectedAt/ingestedAt` 三时间戳语义与顺序约束。
- **建议**：新增一节"时间与时区规范"，统一定义时间戳分层（事件时间/采集时间/入库时间）、时区标识、业务日边界、跨时区统计的换算规则。

### M-4　通知渠道枚举缺失（需求缺失）

- **位置**：§10（L985-1010）、§15.2"Notification 配置"（L1307）
- **问题**：全文只定义通知的"记录/投递/尝试"与人工闭环，但**未定义 V1 支持哪些通知渠道**（邮件 / Webhook / IM 等）及其配置方式，`Delivery` 无法落地。
- **建议**：§10.1 补充 V1 通知渠道清单（建议最小集：Webhook + 至少一种 IM/邮件），并给出渠道级配置项（地址、超时、重试、凭证存放位置）。

### M-5　敏感字段/脱敏规范多处重复、无统一清单（数据定义不明确 / 前后不一致）

- **位置**：§4.2.11（L374）、§4.3.6（L444-446）、§9.2（L932-944）、§11.4（L1074）
- **问题**：密码/验证码/Token/Cookie/Authorization/密钥等敏感信息在四处重复罗列，表述不完全一致，且无一份统一的"敏感字段清单 + 脱敏/掩码策略"。
- **建议**：收敛为单一"数据脱敏与敏感字段规范"（可放 §11），定义敏感字段全集、脱敏算法（hash/掩码/删除）、日志与 Evidence 各自的输出策略，其余章节改为引用。

### M-6　采集与重算边界条件缺失（边界条件缺失）

- **位置**：§6.2.6（L603）、§4.1.6（L230-234）、§6.10（L706-714）
- **问题**：
  1. 只要求"不得假设 SELECT 能发现物理删除"，未规定物理删除如何处理（接受漏采 / 需软删标记 / 全量对账）；
  2. "迟到数据"无迟到阈值定义，也无历史窗口重算的版本保留上限（"保留新旧版本"但保留几个？）；
  3. Event 状态 `SUPERSEDED` 与源版本变化（§6.9 L704）的触发/保留策略未说明。
- **建议**：分别补充：物理删除的 V1 取舍声明与对账机制；迟到阈值（建议按配置）+ 重算版本保留上限；SUPERSEDED 的触发与保留规则。

### M-7　术语表覆盖不全（数据定义不明确）

- **位置**：§1.3（L35-54）
- **问题**：正文反复使用但术语表未收录的概念较多：RiskScore、Severity、MetricType（COUNTER/GAUGE/…）、CollectionStatus、Collection Commit 三态、Event 状态、报告一致性三态（POINT_IN_TIME/BEST_EFFORT/PARTIAL）、PersistenceTransactionCoordinator、RTM/TBD/ADR、DSH-ADP/DSH-RUN 等。
- **建议**：补齐上述术语，并保持"一个术语一份定义"，避免像 DataQuality 与 CollectionStatus 那样仅靠一句"不得混为一谈"来区分。

### M-8　"取消"是硬需求但实现能力未验证、合同未澄清（技术实现矛盾）

- **位置**：§13.3（L1186-1196）、§6.5（L648）
- **问题**：§6.5 要求 TAIL"必须具备超时、取消"、§13.3 要求区分 Timeout/Cancellation，但 §13.3 同时声明"DSH Tool 超时不能强制终止同进程任意代码、取消能力经 RC.5 验证确认"。需求侧"必须取消"与实现侧"取消是协作式、待验证"之间缺乏一个明确的合同边界。
- **建议**：在 §13.3 明确"取消"为**协作式取消**（执行体配合 `AbortSignal`/检查点退出），明确"不承诺强杀"；并把"取消"的验收标准写成可测断言（如"取消后 N 秒内执行体停止推进检查点并释放资源"）。

### M-9　BR-001 关键字段缺枚举定义（数据定义不明确）

- **位置**：§4.1.3（L190-196）
- **问题**：`交易状态`、`交易类型`、`交易币种`仅列名称无枚举，与 §4.1.4"默认只统计业务成功状态"直接冲突——"业务成功状态"的取值集合未定义；对比 BR-002 的认证结果给了 8 个枚举，此处明显缺失。
- **建议**：补 `TransactionStatus` 最小枚举（含业务成功集的定义边界，并声明"具体映射由数据源配置决定"）、`交易类型`、币种规范（建议 ISO-4217）。

## 4. 建议优化（Minor）

- **m-1　状态枚举体系重叠未映射**：§6.6 CollectionStatus、§6.7 DataQuality、§6.10 Event 状态、§5.6 覆盖率状态四套枚举存在语义重叠（如 STALE vs "数据过期"），建议画一张枚举映射/区分图，明确各各自的生命周期范围。
- **m-2　traceId / requestId / correlationId 语义未定义**：§4.3.4 与 §6.9 同时出现三者，未说明其关系与区别；建议在 §6.9 定义三者的生成方与关联规则。
- **m-3　编号类型声明未使用**：§19.1 声明 CONS/DIFF/CR/GAP 四类编号，但全文无一条实例与登记方式说明；建议补齐用法或从清单移除并说明去向。
- **m-4　幂等键粒度未对齐**：§4.1.7 幂等键=租户+数据源+表+主键+源版本，§12.4 幂等按"同 Hash/不同 Hash"判定，两者粒度关系未说明；建议统一给出幂等键 → Hash 的计算契约。
- **m-5　配置项清单缺 Schema 归属声明**：§15.2 列 15 类配置但无 Schema 结构，且未声明"具体 Schema 由 DOC-07 定义"；建议补一句归属声明，避免读者误认为 SRS 已定义 Schema。
- **m-6　请求阶段串联键未说明**：§4.3.3 四个请求阶段（REQUEST_RECEIVED/AUTHENTICATED/…）未说明如何通过 requestId 串联为一次调用；建议明确阶段间以 `requestId/traceId` 关联、以及"不得混合计算同一请求总量"的判定依据。

## 5. 整改优先级与建议顺序

1. **第一优先级（冻结前必须）**：C-2（技术基线）→ C-1（工具需求）→ C-3（风险状态机）→ C-4（AT/TBD 量化）→ C-5（版本一致性）。
2. **第二优先级（详细设计前）**：M-9、M-2、M-3、M-6、M-4、M-5（数据与边界定义，直接阻塞 DOC-03/04 数据模型与接口契约）。
3. **第三优先级（实现与测试前）**：M-1、M-8、M-7（状态转换规则、取消合同、术语补齐）。
4. **随迭代完善**：全部 Minor 项。
